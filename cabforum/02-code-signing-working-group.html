About This Report

This is an experimental, AI-driven research project from SRL. SRL is independent, with no outside funding and no sponsors. This tracker is a summarized pull of the public record, kept as a coherent, concise news update. It draws on the CA/Browser Forum’s own ballots, mailing lists and published documents, and on the public sources of the browser root programs. An AI model reads those sources and writes the summary, and every statement links to the source it came from. Where two sources disagree, both are reported. AI makes mistakes, so check the linked source before relying on any statement. The tracker is updated each week that the public record shows a change.

The Code Signing Working Group writes the rules for the certificates that sign software. It is a smaller and slower group than the one governing web server certificates. Section 1 covers the published requirements and the ballots that produced them. Section 2 covers the ballots in progress, and Section 3 covers the one software platform that sits in the group as a certificate consumer.

A warning about sourcing belongs at the front of this part. The Forum publishes two pages for this group, one listing ballots and one listing requirements, and they still disagree about which version is current. The ballots page presents version 3.8 from August 2024 as the latest release [1]. The requirements page correctly shows version 3.11.0 [2]. Anyone reading only the first page would be wrong by three releases.

1. Published Requirements and the Ballots Behind Them

Every numbered version of the Code Signing Baseline Requirements comes from a ballot. The version history is the record of what the group has actually agreed, as distinct from what it has debated.

Recent Developments

The current version is 3.11.0, adopted through Ballot CSC-32 [2]. Version 3.12.0 is next, and Section 2 explains why it cannot publish before late November [3]. Its intellectual property review ended without objections on 16 June 2026 [4]. It makes a Reserved Policy OID mandatory in subscriber certificates [2]. That rule has been in force since its effective date of 15 September 2026 [2].

Version 3.10 came from Ballot CSC-31, titled Maximum Validity Reduction, which passed on 17 November 2025 [5] [2]. The group is following the same direction as the server certificate rules, shortening the time a signing certificate stays valid. Version 3.9 came from Ballot CSC-26 and covered timestamping private key protection [2]. Version 3.8 came from Ballot CSC-25 and folded the Extended Validation Code Signing Guidelines into the Baseline Requirements [2].

Current State

The Forum’s software repository does not match its website either. Its releases page lists version 3.8 as the newest release, and versions 3.9, 3.10 and 3.11 were never tagged there [6]. The requirements page is the record to read for the version in force [2].

The group has twice rejected wholesale alignment with the server certificate rules. Ballot CSC-030, the June 2025 alignment ballot, failed [7]. Ballot CSC-029, the March 2025 alignment ballot, failed before it [8]. Two failures on the same kind of proposal say something about this group’s appetite for importing another group’s changes as a block.

2. Ballots Now Open

Two ballots are in progress, one that has passed and sits in intellectual property review, and one that has not moved since June. Neither has yet changed the published text.

Recent Developments

Ballot CSC-034 passed on 27 October. It clarifies how the organization name field is used when the certificate subject is a natural person [9]. Dimitris Zacharopoulos of HARICA proposed it on 6 October, with endorsements from eMudhra and Sectigo [9]. Its draft first appeared as a pull request on 24 September [10].

Voting ran from 14 October to 21 October at 17:00 UTC [11]. Microsoft, the group’s only certificate consumer, voted in favour on 20 October after the chair reminded the list that a consumer vote was needed [11].

The chair posted the result on 27 October. All seven voting certificate issuers were in favour, namely Actalis, Certum, eMudhra, HARICA, IdenTrust, Sectigo and SSL.com [12]. Microsoft’s vote was the one consumer vote, also in favour [12]. No vote was against and none abstained, and the quorum for the ballot was four [12].

Current State

The ballot is in intellectual property review, and it is not yet a requirement. The review notice, posted the same day, runs from 27 October at 09:00 UTC to 26 November at 09:00 UTC [3]. It attaches the redline for version 3.12.0 of the requirements [3]. Version 3.12.0 therefore cannot publish before the review ends, and version 3.11.0 stays current until then [3] [2].

The group’s ballots page lists the ballot under its review stage [1]. No exclusion notice had appeared by 1 November [13].

Two small oddities are on the record. SHECA appeared as a yes vote in the voting thread but is not in the counted list, and the results post gives no reason [12]. The review notice cites version 1.3 of the intellectual property policy, while the notices for two other ballots of the Forum cite version 1.4 [3]. The pull request carrying the change is still open and unmerged [10].

One drafting slip is visible in the text. The ballot’s purpose section cites version 3.11 of the requirements, while its motion says the changes are based on version 3.10 [9].

Ballot CSC-033 is a third attempt at alignment with the server certificate rules, and it is stalled. DigiCert proposed it with endorsements from HARICA and Sectigo, and its discussion period opened on 26 May 2026 [14]. It would import three server certificate rules with future dates [14]. These are a recommendation to lint certificates before issuance, a requirement to check for weak private keys, and a requirement to refresh status responses on a set schedule [14].

Discussion was due to end no earlier than 2 June, and no vote has been called since [14]. The last public replies, on 8 June, raised a cross-reference typo, a broken link and syntax fixes [15]. No result or withdrawal has been posted, and its pull request has not changed since 26 May [15].

The group’s earlier minutes point the same way as CSC-033. In May the group agreed on 15 March 2027 as the effective date for both a linting requirement and weekly weak-key checks [16]. A ballot raising the minimum RSA key size for root and subordinate certificates was also under way then [16]. It mirrors a change the S/MIME group has already published, which Part 3 describes.

Unresolved Conflicts

The record of post-quantum signing in this group is thin. A draft to add ML-DSA to the code signing rules was closed without being merged on 29 June 2026, and no replacement has been opened [17]. The group’s web pages and its repository both show no post-quantum ballot at any stage [1] [17]. A new pull request or a ballot announcement would show that the question has returned.

3. The Certificate Consumer

A certificate consumer is the software maker whose platform decides which code signing certificates to trust. In this group that is Microsoft alone.

Recent Developments

The week’s key compromise reached code signing. Two of the eight eMudhra intermediate authorities whose private keys were found recoverable on 17 October issue code signing certificates and are trusted by Microsoft [18]. The other six issue website certificates, and Part 4 tells the whole story [18]. The two code signing authorities were revoked by eMudhra with the rest on 18 October [18].

Microsoft has since published its own response, dated 26 October and revised on 27 October [19]. It confirms eight compromised subordinate authorities, six for websites and two for code signing, and calls it a third-party incident, not a compromise of Microsoft systems [19]. The two code signing authorities are the G3B and G3C intermediates under emSign Root CS CA - G3, each also cross-signed under Sectigo’s AAA Certificate Services, and eMudhra and Sectigo have revoked them [19].

A Windows update on 20 October blocked the eight keys [19]. On 26 October another update removed six emSign G3 roots from the Windows trust list, among them the code signing root and the time stamping root, together with the AAA Certificate Services cross-sign [19]. Edge removed the same seven certificates on 27 October [19]. Customers are told not to restore trust in an affected hierarchy without understanding the risk [19].

Current State

The group has 14 certificate authorities as members, with Microsoft as the only certificate consumer [20]. The chair is Martijn Katerbarg of Sectigo, who stays in the role for the term from 1 December [20] [21]. Dean Coclin of DigiCert was confirmed as the incoming vice-chair in October [21]. Tim Callan left Sectigo for Microsoft PKI Services on 1 November and will stay in the Forum as a Microsoft representative [22]. Part 6 covers the wider Forum elections.

Microsoft’s rules sit in its Trusted Root Program repository, which it names as the official source over its older documentation pages [23]. The newest changes there are the eMudhra announcements of 26 and 27 October, and before them a 28 August change that concerned its post-quantum pilot [24] [25]. For roots submitted from 1 July 2026, code signing must have its own root, separate from server and email roots [26]. Such a root may also cover client authentication and time stamping [26].

The older documentation page still carries the specific code signing rules [27]. New code signing and time-stamping roots must use 4096-bit RSA keys, and elliptic curve keys are not accepted for code signing [27]. Extended Validation code signing stopped being recognised in February 2024 [27]. An authority that issues code signing certificates must also run a time-stamping service [27].

The Extended Validation change shows up for developers. An Extended Validation certificate no longer bypasses Windows reputation checks, so both kinds of certificate must build reputation through downloads [28]. Store packages are re-signed by Microsoft and get full reputation, while ordinary installers need a signature chaining to a program member [28]. Microsoft recommends its Artifact Signing service, formerly Trusted Signing, for software outside the Store [28]. Its documentation for that service was revised again on 27 October, apparently to add troubleshooting for identity validation errors, and its program statements are unchanged [29] [30].

Signing rules for other platforms, such as Java and Adobe, are not covered in this edition. Adobe’s trust list page refused access again, and the Java position could not be verified from a primary source. Their absence here is a gap, not a finding.
