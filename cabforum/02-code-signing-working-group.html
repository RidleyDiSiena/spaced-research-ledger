The Code Signing Working Group writes the rules for the certificates that sign software. It is a smaller and slower group than the one governing web server certificates, and its recent record contains a useful lesson about reading a standards body correctly. Section 1 covers the published requirements and the ballots that produced them. Section 2 covers the work now in progress.

A warning about sourcing belongs at the front of this part. The Forum publishes two pages for this working group, one listing ballots and one listing requirements, and during preparation they did not agree about which version is current. The ballots page presents version 3.8 from August 2024 as the most recent release. The requirements page correctly shows version 3.11.0. Anyone reading only the first page would conclude that nothing has shipped since 2024, and would be wrong by three releases.

1. Published Requirements and the Ballots Behind Them

Every numbered version of the Code Signing Baseline Requirements comes from a ballot. The version history is the record of what the group has actually agreed, as distinct from what it has debated.

Recent Developments

The current version is 3.11.0, adopted by Ballot CSC-32 on 16 June 2026 [1]. It makes inclusion of a Reserved Policy OID mandatory for subscriber certificates, and its effective date is 15 September 2026 [1]. That date is close, which makes this the most immediately operational item in this part.

Version 3.10 came from Ballot CSC-31, titled Maximum Validity Reduction, which passed on 17 November 2025 and took effect on 7 November 2025 [1] [2]. The group is therefore following the same direction of travel as the server certificate rules, shortening the period for which a signing certificate stays valid.

Two earlier versions fill out the recent record. Version 3.9 came from Ballot CSC-26 and covered timestamping private key protection [1]. Version 3.8 came from Ballot CSC-25 and imported the Extended Validation Code Signing Guidelines into the Baseline Requirements, consolidating two documents into one [1].

Current State

The group has rejected alignment with the server certificate rules twice. Ballot CSC-030, the June 2025 alignment ballot, failed [3]. Ballot CSC-029, the March 2025 alignment ballot, failed before it [4]. Two consecutive failures on the same kind of proposal is a signal about this group’s appetite for importing another group’s changes as a block, rather than a single unlucky vote.

Work in progress points in two directions. The group reached consensus on 15 March 2027 as the effective date for both a linting requirement and weekly weak-key checks [5]. Separately, a ballot raising the minimum RSA key size for root and subordinate certificates is under way [5]. It mirrors the change the S/MIME group has already published, which Part 3 describes.
