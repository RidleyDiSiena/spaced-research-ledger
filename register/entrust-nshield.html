Notes

  • ML-KEM, PKCS#11: A CITED none, and the sharpest justification for this column in the register. The device implements ML-KEM – the primitive cell above says so on the same vendor’s word – and an application cannot reach it through PKCS#11 at all, only through Entrust’s proprietary nCore API. A register with only a primitive column would show this device as ML-KEM-capable and leave the reader to discover the interface gap after buying it. “Currently” is the vendor’s word and this cell should be rechecked when Security World moves.
  • ML-DSA, Primitive: Natively in firmware, which Entrust distinguishes from its earlier Post-Quantum Option Pack – that pack made the pre-standard candidates (Dilithium, Kyber, SPHINCS+, Falcon) available inside the CodeSafe execution environment from 2022, which is a different and weaker claim than firmware support for the ratified standards.
  • ML-DSA, PKCS#11: All three parameter sets, through the standard interface.
  • ML-DSA, Firmware signing: The security policy for certificate 5329 lists the start-up integrity tests: “The bootloader integrity is verified using RSA with 4096 bit key and SHA2-256, using NSBIK public key. The firmware integrity is verified using RSA with 4096 bit key and SHA2-256 using NFIK public key.” Both halves of the chain are RSA. THE PATTERN ACROSS THIS CATEGORY, now evidenced rather than suspected: the hardware security modules that hold FIPS-validated post-quantum algorithms FOR CUSTOMERS still sign their OWN firmware classically. Thales Luna T7 uses RSA-4096, Entrust nShield 5s uses RSA-4096, Utimaco uses ECDSA. Crypto4A is the exception and dual-signs with HSS. This is exactly what the firmware column was added to expose: a module whose customer keys are post-quantum and whose root of trust is RSA has moved the problem rather than solved it, and the firmware signing key is the longest-lived key in the device.
  • SLH-DSA, PKCS#11: “SLH-DSA … The following operations are available using this new algorithm: Key generation, Signature generation in pure and prehashed mode, Signature verification in pure and prehashed mode. THIS FUNCTIONALITY IS CURRENTLY ONLY AVAILABLE VIA nCore.” The second cited none in this component’s PKCS#11 column, alongside ML-KEM, and together they make the case for the column better than any argument could: on one device, in one release, ML-DSA reaches PKCS#11 and ML-KEM and SLH-DSA do not. A register with only a primitive column would show all three as supported and leave an integrator to discover the difference after committing.
  • LMS / HSS, Primitive: THE GAP ASKED WHICH OF TWO CLAIMS APPLIED, and the answer is both, to different products. The Security World 13.9 release notes enumerate the post-quantum algorithms the FIRMWARE gained – ML-KEM (FIPS 203), ML-DSA and Pre-Hash ML-DSA (FIPS 204), SLH-DSA (FIPS 205) – and LMS is not among them; the words LMS and Leighton do not appear in 50,000 characters of notes. What does offer LMS is the separate Post-Quantum Option Pack, which Entrust describes as enabling “NIST approved code-signing with the Leighton-Micali Signature (LMS)” inside the CodeSafe execution environment. That is exactly what this scale calls experimental: a separate add-on the project itself ships, rather than something the shipping firmware does.
