Notes

  • ML-KEM, Primitive: experimental is exactly what the scale means by a preview channel, and the contrast inside one service is the useful part: signatures are generally available, key encapsulation is in preview. A migration plan that assumes both are equally ready would be wrong about half of it.
  • ML-DSA, Primitive: The vendor frames this as a way for CUSTOMERS to build post-quantum roots of trust for firmware signing. That is the firmware column’s question asked of somebody else’s product, not of this one: this register’s firmware column is about the component’s own image, and a cloud service does not ship one to you.
  • SLH-DSA, Primitive: One of only three components in the register that offer SLH-DSA at all – the others being Crypto4A and Entrust – and the only cloud service among them. The hash-based signature scheme is the conservative choice a customer reaches for when they do not want to bet on lattices, so a service offering it is a different proposition from one offering ML-DSA alone.

Known Unknowns

Cells an engineer would ask about that no cited source has settled yet. not checked means nobody has searched. searching means fewer than 2 passes are done. none found means the search was completed and came back empty, and the artifacts examined are named; a result older than 90 days is marked for recheck.

  • ml-dsa / pkcs11 – no public answer, checked 2026-09-13: Searched to exhaustion and the artifact that would settle it is NOT PUBLIC. The PKCS#11 library is real and documented – integration pages cover OpenSSL, Apache TLS termination, NGINX TLS offload, pkcs11-tool, Jsign and a Windows CNG provider – but no mechanism or algorithm list says whether the post-quantum key types are among them. Nobody should search again until Google publishes one; this is not a question more effort answers. Examined: Cloud KMS PKCS #11 library documentation (overview and integration pages), Cloud KMS digital signatures reference.
  • ml-dsa / fips – searching, 1 of 2 passes: Google states FIPS 140-3 Level 3 for Cloud HSM protection level generally, but the register’s question is whether ML-DSA is on the approved-algorithm list of the module behind it – and Google does not name that module publicly. The 2026-09-13 CMVP scan found no Google Cloud KMS or Cloud HSM module under Google’s own vendor name; Cloud HSM is understood to run on third-party HSM hardware, whose certificate would be the answer. Naming that vendor without a Google statement would be exactly the plausible-looking guess this register refuses. Second pass: a Google statement naming the module, or its security policy. Examined: CMVP validated module search, vendor Google (32 certificates, none a Cloud KMS or Cloud HSM module), CMVP Modules In Process list, Cloud KMS digital signatures reference.
