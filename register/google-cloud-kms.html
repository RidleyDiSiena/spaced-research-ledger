Where the Cryptography Comes From

This component does not implement everything it is asked about. What it inherits, from what, and at which version:

  • Marvell LiquidSecurity, not tracked in this register – platform, pinned at certificate #4399, FIPS 140-2 Level 3, listed by NIST as Historical. Inherits: FIPS 140-3. Google names the hardware and the certificate itself: “Cloud HSM uses Marvell LiquidSecurity HSMs” and “For more information about our certification, see Certificate #4399”. Marvell is NOT a component in this register – it was deliberately deferred on 2026-09-13 because its public material claims crypto-agility without naming a single shipped post-quantum algorithm – so this is an external edge, and the register records nothing about its standing beyond what Google states. What can be said is on the ml-dsa/fips cell: that certificate is FIPS 140-2 and NIST lists it as Historical, so it cannot carry a post-quantum algorithm at all. If Marvell ever becomes a component, the promotion invariant will catch this edge and require it. [6] [7]

FIPS 140-3

Google Cloud KMS holds no FIPS 140-3 certificate of its own. It takes its cryptography from Marvell LiquidSecurity (platform, at certificate #4399, FIPS 140-2 Level 3, listed by NIST as Historical), and Marvell LiquidSecurity is not a component in this register, so nothing about its FIPS standing is recorded here – and its absence from these pages is not a finding about it. Running in an approved mode also needs the validated version on a tested operating environment, which no register can tell you.

Notes

  • ML-KEM, Primitive: experimental is exactly what the scale means by a preview channel, and the contrast inside one service is the useful part: signatures are generally available, key encapsulation is in preview. A migration plan that assumes both are equally ready would be wrong about half of it.
  • ML-DSA, Primitive: The vendor frames this as a way for CUSTOMERS to build post-quantum roots of trust for firmware signing. That is the firmware column’s question asked of somebody else’s product, not of this one: this register’s firmware column is about the component’s own image, and a cloud service does not ship one to you.
  • ML-DSA, FIPS 140-3: GOOGLE NAMES THE MODULE, WHICH THE GAP WAS WAITING FOR, and the answer is older than expected. The Cloud HSM architecture document says: “Cloud HSM uses Marvell LiquidSecurity HSMs (models CNL3560-NFBE-2.0-G and CNL3560-NFBE-3.0-G)” and “For more information about our certification, see Certificate #4399”. That certificate is FIPS 140-2, not 140-3, and NIST lists it as HISTORICAL – “should not be included by Federal Agencies in new procurements”. ML-DSA cannot be on it: FIPS 204 postdates the 140-2 programme entirely. So Google’s “FIPS 140-3 Level 3” framing for the protection level is about the service’s posture rather than about this certificate, and the ML-DSA keys Cloud KMS holds are not inside a validated post-quantum boundary. The third instance today of one pattern: a vendor’s true sentence about a validated module, and a different answer once you read the certificate. Marvell is not a component in this register – it was deliberately deferred on 2026-09-13 for naming no shipped post-quantum algorithm – so the coupling is recorded as an external edge below.
  • SLH-DSA, Primitive: One of only three components in the register that offer SLH-DSA at all – the others being Crypto4A and Entrust – and the only cloud service among them. The hash-based signature scheme is the conservative choice a customer reaches for when they do not want to bet on lattices, so a service offering it is a different proposition from one offering ML-DSA alone.

Known Unknowns

Cells an engineer would ask about that no cited source has settled yet. not checked means nobody has searched. searching means fewer than 2 passes are done. none found means the search was completed and came back empty, and the artifacts examined are named; a result older than 90 days is marked for recheck.

  • ml-dsa / pkcs11 – no public answer, checked 2026-09-13: Searched to exhaustion and the artifact that would settle it is NOT PUBLIC. The PKCS#11 library is real and documented – integration pages cover OpenSSL, Apache TLS termination, NGINX TLS offload, pkcs11-tool, Jsign and a Windows CNG provider – but no mechanism or algorithm list says whether the post-quantum key types are among them. Nobody should search again until Google publishes one; this is not a question more effort answers. Examined: Cloud KMS PKCS #11 library documentation (overview and integration pages), Cloud KMS digital signatures reference.
