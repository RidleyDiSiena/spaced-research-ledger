Where the Cryptography Comes From

This component does not implement everything it is asked about. What it inherits, from what, and at which version:

  • Windows CNG – platform. Inherits: FIPS 140-3. Schannel performs no cryptography of its own; it calls CNG, which is where Windows’ validated modules live. Its FIPS standing is therefore CNG’s, and the pointer says so rather than repeating it. [6]

FIPS 140-3

Schannel holds no FIPS 140-3 certificate of its own. It takes its cryptography from Windows CNG (platform), and Windows CNG holds FIPS 140-3 certificate 5313. Whether a given algorithm is inside that validated boundary is Windows CNG’s answer, not this component’s: see the Windows CNG page. Running in an approved mode also needs the validated version on a tested operating environment, which no register can tell you.

Notes

  • X25519MLKEM768, TLS 1.3: Not-default confirmed by Microsoft’s own FAQ (2026-09-28): “No not by default; you must enable it.” THE GROUP, NAMED AT LAST, which is what this gap was waiting for: “the client sends a key_share, pre-generating and attaching the ephemeral public keys for its top pick (X25519MLKEM768) so the handshake can finish in one round trip if the server agrees”, and a worked example shows a negotiated connection reporting TLS 1.3 with the group X25519MLKEM768. So Schannel can now be recorded on the named-group row rather than only on the KEM family. available: Microsoft states the post-quantum groups are not enabled by default and must be set up, using the same mechanisms as existing TLS ECC curves.
  • SecP256r1MLKEM768, TLS 1.3: Vendor enumeration of Schannel groups: secp256r1_mlkem768 (TLS 1.3) is listed as supported by the Microsoft Schannel Provider but not enabled by default, and marked not available in FIPS mode (legacy). Available rather than default for that reason. Found by the 2026-09-27 patrol.
  • SecP384r1MLKEM1024, TLS 1.3: Vendor enumeration of Schannel groups: secp384r1_mlkem1024 (TLS 1.3) is listed as supported by the Microsoft Schannel Provider but not enabled by default, and marked not available in FIPS mode (legacy). Available rather than default for that reason. Found by the 2026-09-27 patrol.
  • MLKEM768, TLS 1.3: KB5120998 (2026-08-27 optional preview, builds 26100/26200.9278): “ML-KEM can now be used as a standalone algorithm for TLS key exchange, in addition to hybrid groups added previously.” In the GA cumulative KB5124008 (2026-09-08), which includes KB5120998 – but the Release Preview notes put it under “Gradual rollout”, so not every device has it yet. Microsoft’s TLS PQC FAQ (2026-09-28, Q13) names the groups: “you use only MLKEM768 or MLKEM1024 if CNSA 2.0 compliance is in scope”. Opt-in like every Windows PQ group. SERVER 2025, found 2026-10-15: KB5126646 (2026-10-13) “adds support for ML-KEM post-quantum key exchange in TLS 1.3” – the first Server 2025 KB to say ML-KEM at all (the 2026-10-04 and 10-08 checks found none). Server 2025 already had the three hybrids from KB5099536 (2026-07-14), so the new line most plausibly is the standalone groups reaching Server 2025, but the KB does not say standalone or name MLKEM768/MLKEM1024, so since is left at the Windows 11 KBs and the Server 2025 addition is for the user to rule on. The Windows 11 cumulative of the same day, KB5127648 (26300/26200/26100.9711), has no TLS or ML-KEM text.
