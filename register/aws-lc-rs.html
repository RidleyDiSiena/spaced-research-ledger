Where the Cryptography Comes From

This component does not implement everything it is asked about. What it inherits, from what, and at which version:

  • AWS-LC – linked, pinned at AWS-LC-FIPS 3.0.x per aws-lc-fips-sys; the certified module on that line is 3.1.0. Inherits: Primitive, FIPS 140-3. The crate is a Rust binding over AWS-LC: docs.rs lists aws-lc-sys for the ordinary build and aws-lc-fips-sys for the FIPS one among its dependencies. The FIPS module that binding carries was traced on 2026-09-13 – AWS-LC-FIPS 3.0.x by the crate’s own README – which settled the ml-dsa/fips cell (ML-DSA is in no AWS-LC certificate at all) and left one minor-version question open, recorded as the ml-kem/fips gap. The pinned value states both halves rather than choosing one. [6] [7]

FIPS 140-3

aws-lc-rs holds no FIPS 140-3 certificate of its own. It takes its cryptography from AWS-LC (linked, at AWS-LC-FIPS 3.0.x per aws-lc-fips-sys; the certified module on that line is 3.1.0), and AWS-LC holds FIPS 140-3 certificates 5429, 5314, 5298, 5146, 4816, 4631, and has 2 modules in the CMVP queue. Whether a given algorithm is inside that validated boundary is AWS-LC’s answer, not this component’s: see the AWS-LC page. Running in an approved mode also needs the validated version on a tested operating environment, which no register can tell you.

Notes

  • ML-KEM, Primitive: The kem module documents ML_KEM_512, ML_KEM_768 and ML_KEM_1024 as a stable public API, not behind the unstable feature flag that gated ML-DSA until 1.18.1. The docs name no introducing version.
  • ML-DSA, Primitive: Stable API without the unstable feature flag from 1.18.1; described as not fully stabilised in February 2026.
  • ML-DSA, FIPS 140-3: RESOLVED 2026-09-13, downgraded from available after the verification the earlier flag asked for. The chain, end to end: aws-lc-rs’s FIPS build pulls aws-lc-fips-sys, whose own README says it binds AWS-LC-FIPS 3.0.x (branch fips-2024-09-27); AWS’s FIPS.md attributes certificates 5298 (dynamic) and 5314 (static) to that module line; and the security policy for 5314 – read in full – does not contain the string ML-DSA anywhere, not even among the non-approved algorithms, while ML-KEM appears 101 times. So ML-DSA is in the FIPS-branch library the crate builds and is NOT in the validated boundary of any AWS-LC module NIST has certified, which is exactly what this scale calls experimental: in a module build that is not the validated one. The crate’s own release note (“including under FIPS”) is about the FIPS BUILD, and that was the ambiguity: a FIPS build is not a FIPS validation. One thread is deliberately left hanging rather than papered over – see the ml-kem/fips gap: the crate documents binding 3.0.x while the certified module is 3.1.0, and no public document read on 2026-09-13 closes that minor-version gap. It does not affect THIS cell, because ML-DSA is absent under either version.

Known Unknowns

Cells an engineer would ask about that no cited source has settled yet. not checked means nobody has searched. searching means fewer than 2 passes are done. none found means the search was completed and came back empty, and the artifacts examined are named; a result older than 90 days is marked for recheck.

  • ml-kem / fips – no public answer, checked 2026-09-13: Searched to exhaustion; the document that would close it does not exist publicly. ML-KEM IS inside the validated boundary – the security policy for certificate 5314 names it 101 times – and what cannot be established is that the module this CRATE bundles is that module: aws-lc-fips-sys documents binding AWS-LC-FIPS 3.0.x, and AWS’s own certificate list has entries for v1.0, v2.0, v3.1 and NetOS but none for v3.0. Writing available would assert a minor-version match nobody published. Reopen when AWS states which module version a released crate carries. Examined: aws-lc-fips-sys README (main branch and the published 0.14.2 crate page), aws-lc crypto/fipsmodule/FIPS.md certificate list, CMVP security policy 140sp5314.pdf (module version AWS-LC FIPS 3.1.0).
