Where the Cryptography Comes From

This component does not implement everything it is asked about. What it inherits, from what, and at which version:

  • aws-lc-rs – provider, pinned at aws-lc-rs ^1.18 (rustls 0.23.44). Inherits: FIPS 140-3. rustls does no cryptography itself; it takes a provider crate, and aws-lc-rs is the default. It is one of two providers – the other is recorded as the ring edge below rather than left in this sentence, so the page cannot read as though rustls had a single backend. [8] [9]
  • ring, not tracked in this register – provider. Inherits: FIPS 140-3. The other provider crate rustls can be built on, listed beside aws-lc-rs as an optional dependency of rustls 0.23.44. ring is NOT a component in this register, so a rustls built on ring inherits nothing recorded here – and that is a gap in this register’s coverage, not a finding about ring. Recorded as an edge rather than a remark so the count of backends is right and the promotion to a real component is a one-line change if ring is ever tracked. [10]

FIPS 140-3

rustls holds no FIPS 140-3 certificate of its own, and there is no single answer for it: which of its 2 backends this build carries decides, and that is a build-time choice no register can see. Running in an approved mode also needs the validated version on a tested operating environment, which no register can tell you. What each backend holds:

  • aws-lc-rs (provider, at aws-lc-rs ^1.18 (rustls 0.23.44)) holds no certificate of its own and takes its own cryptography from AWS-LC. See aws-lc-rs.
  • ring (provider) is not a component in this register, so nothing about its FIPS standing is recorded here – and its absence from these pages is not a finding about it.

Notes

  • X25519MLKEM768, TLS 1.3: In the aws-lc-rs provider’s default list since 0.23.22, so default on this register’s scale (was available, corrected 2026-10-15 under the standing hybrid-groups check, the same correction the 2026-10-08 pass made for seven other components). Nuance the status cannot carry: without the prefer-post-quantum feature the hybrid is offered LAST, after X25519, secp256r1 and secp384r1, so a client built with default features sends a classical key_share and reaches the hybrid only if the server insists via HelloRetryRequest; with the feature it is first. Merged into the core crate at 0.23.22, having previously lived in the experimental rustls-post-quantum crate. The ring provider has no post-quantum group at all. GHSA-w44r-93j7-qv28 (fixed 0.23.46) was a downgrade of exactly this group through poisoned key-exchange hints; see releases.
  • SecP256r1MLKEM768, TLS 1.3: SECP256R1MLKEM768 is a documented group of the same provider.
  • SecP384r1MLKEM1024, TLS 1.3: Absent from the aws-lc-rs provider’s documented key exchange group set, which lists MLKEM768, MLKEM1024, SECP256R1MLKEM768, X25519MLKEM768 and the three classical curves. Recorded as none rather than a gap because that list enumerates what the provider offers.
  • MLKEM512, TLS 1.3: The aws-lc-rs kx_group module exports SECP256R1, SECP384R1, X25519, MLKEM768, MLKEM1024, SECP256R1MLKEM768 and X25519MLKEM768 only (0.23.45 and main).
  • MLKEM768, TLS 1.3: aws-lc-rs provider: MLKEM768 in ALL_KX_GROUPS from v/0.23.22, not in DEFAULT_KX_GROUPS: “by default MLKEM768 is only offered in hybrid with X25519”. The ring provider has no post-quantum group. Replaces the old ml-kem/tls cell, whose evidence was the hybrid rustls-post-quantum crate.
  • MLKEM1024, TLS 1.3: aws-lc-rs provider: MLKEM1024 added by “Add ML-KEM-1024 key encapsulation mechanism” (absent at v/0.23.36), in ALL_KX_GROUPS, not default.
  • ML-DSA, X.509: ML-DSA certificates enabled by default with the aws-lc-rs provider. Primary source added 2026-10-04 (patrol): the project’s GitHub release for 0.23.44 carries the same sentence as the lxer copy, so the claim now rests on the release itself; the lxer entry is kept only as the ledger claim’s trace.
