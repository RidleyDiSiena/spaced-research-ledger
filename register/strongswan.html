Notes

  • ML-KEM, IPsec / IKEv2: available rather than default: you write it into a proposal. WHY IPSEC IS THE EASY CASE, and worth understanding because it is the opposite of TLS: RFC 9370 lets up to seven ADDITIONAL key exchanges be layered on after the first, so ML-KEM is appended to a classical exchange rather than replacing it, and a deployment keeps its existing security properties while adding the new one. The hybrid is built by configuration rather than baked into a named group, which is why this register records it on the ML-KEM row and has no hybrid-group rows for IPsec at all. Four different implementations can supply the mathematics – Botan, wolfSSL, AWS-LC or strongSwan’s own ml plugin – so the answer travels with the build; that is prose here rather than a derives_from edge because strongSwan ships an implementation of its own.
  • ML-DSA, IPsec / IKEv2: Patrol 2026-09-26, closes the gap as planned. The project’s own workshop deck ‘IKEv2 Signature Authentication using ML-DSA’ says the internal ml plugin implementation is work in progress on the ml-dsa branch with 6.1.0 as the ETA; 6.1.0 shipped 2026-09-07 with ML-KEM hardening only and no ML-DSA in NEWS or plugins/ml. Medium confidence on timing.
