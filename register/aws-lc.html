Notes

  • ML-KEM, Primitive: ML-KEM-512/768/1024; implementation imported from mlkem-native v1.1.0 into the FIPS module.
  • ML-KEM, TLS 1.3: Pure ML-KEM groups are listed beside the hybrids.
  • ML-KEM, FIPS 140-3: ML-KEM inside validated FIPS 140-3 modules (certificates 4631, 5314, 5298 as of August 2026). Whether it is on in approved mode by default is not in the claims, so ‘available’ not ‘default’.
  • X25519MLKEM768, TLS 1.3: The project’s post-quantum README lists X25519MLKEM768, SecP256r1MLKEM768 and SecP384r1MLKEM1024 among its supported TLS groups, alongside pure ML-KEM variants. Whether any is offered by default is not stated there.
  • SecP256r1MLKEM768, TLS 1.3: Listed in the same set.
  • SecP384r1MLKEM1024, TLS 1.3: Listed in the same set.
  • ML-DSA, Primitive: ML-DSA-44/65/87.
  • ML-DSA, TLS 1.3: TLS 1.3 signature scheme, per the project’s release history.

Known Unknowns

Cells an engineer would ask about that no cited source has settled yet. not checked means nobody has searched. searching means fewer than 2 passes are done. none found means the search was completed and came back empty, and the artifacts examined are named; a result older than 90 days is marked for recheck.

  • ml-dsa / fips – none found 2026-09-12: Searched twice on 2026-09-12 and found nothing conclusive: the project’s own FIPS-module README names ML-DSA and its three parameter sets but says nothing about validation status or certificate numbers, and the ledger’s evidence for AWS-LC’s validated modules speaks only of ML-KEM. The file living under crypto/fipsmodule/ hints the code sits inside the boundary; that is an inference, not a statement, so the question stays open. A CMVP scan, not another search, is what settles this – see B2. Examined: AWS-LC crypto/fipsmodule/PQREADME.md, CMVP certificate 4631 (cited by the ledger for ML-KEM).
