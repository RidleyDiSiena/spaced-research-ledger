Where the Cryptography Comes From

This component does not implement everything it is asked about. What it inherits, from what, and at which version:

  • OpenSSL – linked. Inherits: Primitive, X.509, FIPS 140-3. The published wheels contain a statically linked OpenSSL binding, per the project’s own installation guide. It is one of two supported backends, so this entry is not the whole answer on its own. [3]
  • AWS-LC – provider. Inherits: Primitive, X.509, FIPS 140-3. The project’s changelog records feature after feature landing “when building against AWS-LC”, so AWS-LC is a supported backend and the answer differs by build. Which one a given install carries is a build-time fact this register cannot see. [4]

FIPS 140-3

pyca/cryptography (Python) holds no FIPS 140-3 certificate of its own, and there is no single answer for it: which of its 2 backends this build carries decides, and that is a build-time choice no register can see. Running in an approved mode also needs the validated version on a tested operating environment, which no register can tell you. What each backend holds:

  • OpenSSL (linked) holds FIPS 140-3 certificates 4985, 4811, 4282, and has a module in the CMVP queue. See OpenSSL.
  • AWS-LC (provider) holds FIPS 140-3 certificates 5429, 5314, 5298, 5146, 4816, 4631, and has 2 modules in the CMVP queue. See AWS-LC.

Notes

  • ML-KEM, Primitive: Native support via Rust bindings and the AWS-LC backend.
  • SLH-DSA, Primitive: The project’s own roadmap issue tracks ML-KEM, ML-DSA and SLH-DSA together. ML-KEM and ML-DSA shipped in 48; SLH-DSA had not, and work was described as started. Recorded as planned on the strength of the tracking issue rather than a release.
