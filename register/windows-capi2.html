Where the Cryptography Comes From

This component does not implement everything it is asked about. What it inherits, from what, and at which version:

  • Windows CNG – platform. Inherits: FIPS 140-3. CAPI2 parses and validates certificates; the signature verification underneath is CNG’s, and so is the FIPS boundary. AD CS states the dependency for the whole Windows PQC surface: “All PQC algorithms require CNG key storage providers.” [5]

FIPS 140-3

Windows CryptoAPI (CAPI2) holds no FIPS 140-3 certificate of its own. It takes its cryptography from Windows CNG (platform), and Windows CNG holds FIPS 140-3 certificate 5313. Whether a given algorithm is inside that validated boundary is Windows CNG’s answer, not this component’s: see the Windows CNG page. Running in an approved mode also needs the validated version on a tested operating environment, which no register can tell you.

Notes

  • ML-DSA, X.509: Read narrowly, and the narrowness is the point. “Certificate functions” is Microsoft’s own name for this layer, so ML-DSA certificate support is stated rather than inferred – but neither document says whether an ML-DSA chain validates by DEFAULT in every caller, which is what default would claim on this scale. Available is the strongest thing the sources support.
  • Composite ML-DSA, X.509: CLOSES A GAP OPENED 2026-09-13, which asked whether CAPI2 can VALIDATE a composite certificate given that AD CS records composite ML-DSA as Phase 2 for ISSUANCE. It can, and the two halves really did ship apart: issuance is still Phase 2 in the AD CS table, while the certificate-handling layer went generally available on 14 July 2026. TWO POINTS OF NUANCE, neither of which changes the status. (1) The July update line says “composite algorithms” without re-naming the two layers, so reading it as covering certificate functions and not only CNG rests on the body sentence that scopes the shipment as one thing across both; the alternative reading – that only CNG went GA – is not supported by anything in the post, which never separates them. (2) The CNG reference page still carries a prerelease warning on the identifier, which is a stale document rather than a contradiction: its last edit predates the GA by six weeks. available and not default for the ordinary reason – nothing states that a composite chain validates without an opt-in, and the composite format is new enough that relying parties are expected to opt in. Composite ML-KEM shipped in the same update and has no row in this register; see PLAN.md.

Known Unknowns

Cells an engineer would ask about that no cited source has settled yet. not checked means nobody has searched. searching means fewer than 2 passes are done. none found means the search was completed and came back empty, and the artifacts examined are named; a result older than 90 days is marked for recheck.

  • ml-kem / x509 – none found 2026-09-14: Second pass done and it found nothing either way, which is the answer: no Microsoft document states whether the Windows certificate functions can handle a certificate carrying an ML-KEM key. What the second pass DID establish is that the silence is not an artifact of the roadmap having stalled – the composite half of the same promise shipped on 14 July 2026 and is now a cell above, while the ML-KEM half did not. So the two capabilities Microsoft announced together in June (“Additional post-quantum capabilities, including ML-KEM and composite algorithm support, are planned later this year”) have diverged, and only one of them can be recorded. Not a none cell: nothing here ENUMERATES what the certificate layer accepts, and this register does not read a document’s silence as a denial. The thing that would settle it is an ML-KEM certificate OID in the wincrypt reference or a CertEnroll page naming the key type; neither exists today. Recheck when the ML-KEM phase ships. Examined: Microsoft PQC GA announcement, 2025-11-18, AD CS post-quantum overview (ML-KEM: Planned, Phase 2), New Windows Features to Secure Today’s Data in a Post-Quantum World, 2026-06-02 with the 2026-07-14 update, CNG algorithm identifiers reference (wincrypt/BCrypt identifier table – ML-KEM present as a CNG primitive, no certificate-side identifier), CertEnroll portal and Certificate Request Functions reference.
