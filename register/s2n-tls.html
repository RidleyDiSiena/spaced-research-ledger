Where the Cryptography Comes From

This component does not implement everything it is asked about. What it inherits, from what, and at which version:

  • AWS-LC – provider. Inherits: FIPS 140-3. s2n-tls performs no cryptography itself. Its README says the library is structured so that different encryption libraries may be used, and names AWS-LC first; AWS-LC is the only supported libcrypto on Windows. Its FIPS standing is whichever libcrypto it was built against. [6]
  • OpenSSL – provider. Inherits: FIPS 140-3. One of the four libcryptos the README names. Listed so the register cannot present any single backend as the answer. [7]
  • BoringSSL – provider. Inherits: FIPS 140-3. One of the four libcryptos the README names. [7]
  • LibreSSL – provider. Inherits: FIPS 140-3. One of the four libcryptos the README names. [7]

FIPS 140-3

s2n-tls holds no FIPS 140-3 certificate of its own, and there is no single answer for it: which of its 4 backends this build carries decides, and that is a build-time choice no register can see. Running in an approved mode also needs the validated version on a tested operating environment, which no register can tell you. What each backend holds:

  • AWS-LC (provider) holds FIPS 140-3 certificates 5429, 5314, 5298, 5146, 4816, 4631, and has 2 modules in the CMVP queue. See AWS-LC.
  • OpenSSL (provider) holds FIPS 140-3 certificates 4985, 4811, 4282, and has a module in the CMVP queue. See OpenSSL.
  • BoringSSL (provider) holds FIPS 140-3 certificates 5296, 5244, 5104, 4735, 4444, 4407, 4156, and has 3 modules in the CMVP queue. See BoringSSL.
  • LibreSSL (provider) holds no certificate of its own. See LibreSSL.

Notes

  • ML-KEM, TLS 1.3: Hybrid ECDH+ML-KEM and pure ML-KEM key exchange; used across AWS service endpoints. Hybrid suites supported only on Linux per AWS KMS documentation (d0001:21).
  • X25519MLKEM768, TLS 1.3: Named in the security policy tables as x25519+mlkem768, alongside secp256r1+mlkem768, secp384r1+mlkem1024 and pure mlkem1024. Reached by choosing a policy, not by default: the documentation says a policy supporting post-quantum must be configured. s2n-tls must be built against AWS-LC for any of it.
  • SecP256r1MLKEM768, TLS 1.3: In the same policy tables as the X25519 hybrid.
  • SecP384r1MLKEM1024, TLS 1.3: In the same policy tables; the CNSA 2.0 pairing.
  • ML-DSA, TLS 1.3: ML-DSA certificates for TLS 1.3 authentication in the default_pq and cnsa_2 policies. Those are named policies, not the library default, so ‘available’.
  • ML-DSA, X.509: An ML-DSA certificate is configured exactly as an RSA or ECDSA one would be.
