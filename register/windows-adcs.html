Where the Cryptography Comes From

This component does not implement everything it is asked about. What it inherits, from what, and at which version:

  • Windows CNG – platform. Inherits: nothing declared. Recorded as a dependency rather than an inheritance, which is why capabilities is empty: AD CS gets no column from CNG, but it cannot issue a post-quantum certificate without it. The page is explicit – “All PQC algorithms require CNG key storage providers. AD CS doesn’t support legacy Cryptographic Service Providers (CSPs).” An administrator whose template uses a legacy CSP gets nothing from this component’s Available cell. [5]

Notes

  • ML-KEM, X.509: A KEM certificate is a real thing AD CS says it will issue, so this is the vendor’s own roadmap rather than an inference.
  • ML-DSA, X.509: Issuance, not validation – a CA minting ML-DSA certificates. Available rather than default because a template has to be configured for it; nothing is issued with ML-DSA unless an administrator asks.
  • SLH-DSA, X.509: An absence read as a finding, on the rule this register uses everywhere: where a source ENUMERATES, a name missing from it is an answer. This table is an enumeration – it says AD CS “adopts the post-quantum algorithms standardized by NIST” and then lists them with a phase each. SLH-DSA is NIST-standardized (FIPS 205) and is not on it, including as a later phase. Revisit when the phases advance.
  • Composite ML-DSA, X.509: The table also carries Composite ML-KEM as Planned (Phase 2). The register has no composite-KEM row – one component carrying it is not yet two, which is the bar for adding a row – so it is recorded here in prose until a second component has it.
