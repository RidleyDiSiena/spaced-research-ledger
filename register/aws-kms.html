Notes

  • ML-KEM, FIPS 140-3: Not in any module of this project: the CMVP validated list and the Modules In Process list were scanned on 2026-09-13 and name none carrying it.
  • ML-DSA, Primitive: External Mu – pre-hashed signing – matters here more than in a library: it is what lets a large object be hashed outside the service and only the digest sent to it. The register records external-mu in cell notes rather than as its own row until two components track it; this is the second mention and the first in a service.
  • ML-DSA, FIPS 140-3: THE FINDING OF THE HARDWARE PASS, and it is a distinction rather than a contradiction. The AWS KMS developer guide says: “AWS KMS creates and protects all ML-DSA keys and signature operations in FIPS 140-3 Security Level 3 validated hardware security modules.” That is true. The 2026-09-13 CMVP scan then read the certificate those modules hold – AWS Key Management Service HSM, certificate 4884, issued 2024-11-18 – and its approved-algorithm list has thirty entries, not one of them post-quantum. Both facts stand together: the MODULE is validated, and ML-DSA is not a validated ALGORITHM within it, so using it means using a non-approved algorithm inside a validated boundary. Nothing is pending either: no AWS KMS HSM appears on the Modules In Process list, which is why this is none and not a gap. This is the same class of claim as the aws-lc-rs one resolved on 2026-09-13 – a FIPS build is not a FIPS validation – wearing different clothes: a validated module is not a validated algorithm. Expect the phrasing again; check the approved list every time.
  • SLH-DSA, FIPS 140-3: Not in any module of this project: the CMVP validated list and the Modules In Process list were scanned on 2026-09-13 and name none carrying it.
  • LMS / HSS, FIPS 140-3: Not in any module of this project: the CMVP validated list and the Modules In Process list were scanned on 2026-09-13 and name none carrying it.
  • XMSS / XMSS^MT, FIPS 140-3: Not in any module of this project: the CMVP validated list and the Modules In Process list were scanned on 2026-09-13 and name none carrying it.

Known Unknowns

Cells an engineer would ask about that no cited source has settled yet. not checked means nobody has searched. searching means fewer than 2 passes are done. none found means the search was completed and came back empty, and the artifacts examined are named; a result older than 90 days is marked for recheck.

  • ml-kem / primitive – searching, 1 of 2 passes: AWS KMS supports ML-KEM, but for the TRANSPORT rather than as a key type: hybrid post-quantum TLS to the KMS endpoints, in non-FIPS endpoints, across the aws partition. That is a different question from whether the service will create and hold an ML-KEM key for you, which is what this cell asks and which no document read answers. The distinction is easy to lose and the reason this is a gap rather than a cell: a reader who sees ‘AWS KMS supports ML-KEM’ in a press release is being told about the connection, not the key. Second pass: the KMS key-spec reference, which enumerates every supported key type. Examined: AWS KMS ML-DSA developer guide, ML-KEM post-quantum TLS now supported in AWS KMS, ACM and Secrets Manager (AWS Security Blog), Using hybrid post-quantum TLS with AWS KMS.
  • ml-dsa / pkcs11 – searching, 1 of 2 passes: AWS KMS is reached through its own AWS API rather than PKCS#11; a PKCS#11 provider for it exists as third-party software, which is a different component’s answer and not this one’s. Recorded as a gap rather than a none because the vendor does not say it anywhere – the absence of a PKCS#11 interface is inferred from the service’s shape, and the register does not read its own inference as a citation. Examined: AWS KMS developer guide, ML-DSA keys.
