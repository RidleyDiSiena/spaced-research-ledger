Thales Luna HSM

Maintained by Thales. Firmware releases on the 7.x line, with a matching Luna HSM Client. Post-quantum support arrived in two steps: LMS-HSS in firmware 7.8.9, ML-KEM and ML-DSA in 7.9.0. Home: https://cpl.thalesgroup.com/encryption/hardware-security-modules

Notes

  • ML-KEM, Primitive: In firmware rather than a loadable functionality module, which is the difference between a supported algorithm and an add-on somebody has to deploy.
  • ML-KEM, FIPS 140-3: Inside Luna T7, Thales Trusted Cyber Technologies, FIPS 140-3 certificate 5450 issued 2026-07-29. Sunset 2031-07-28.
  • ML-KEM, PKCS#11: Through the STANDARD interface rather than a vendor extension, which is the distinction this column exists to make: compare Utimaco, which reaches the same algorithms through vendor-defined mechanisms, and Entrust, which reaches ML-KEM only through its proprietary nCore API.
  • ML-DSA, Primitive: Backup, cloning and high availability all work, which is NOT true of the stateful hash-based keys below – see the LMS/HSS note. One documented limitation: firmware 7.9.0 does not support wrapping or unwrapping ML-DSA private key objects, pending standardisation.
  • ML-DSA, FIPS 140-3: Inside Luna T7, Thales Trusted Cyber Technologies, FIPS 140-3 certificate 5450 issued 2026-07-29. Sunset 2031-07-28.
  • SLH-DSA, Primitive: TWO SOURCES, NEITHER MENTIONING IT, one of them exhaustive. The 89-page security policy for certificate 5450 does not contain the string SLH-DSA ANYWHERE – while mentioning LMS 139 times and ML-DSA 68 – and a security policy has to describe the module’s non-approved services as well as its approved ones, so silence there is close to conclusive for the module. Thales’s own post-quantum documentation agrees, naming LMS-HSS, ML-KEM and ML-DSA and no other family. Read narrowly: this is the module and the documented product, not a promise about future firmware. Crypto4A holds SLH-DSA on an issued certificate today, so this is a product difference rather than a hardware limitation.
  • SLH-DSA, FIPS 140-3: Not in any module of this project: the CMVP validated list and the Modules In Process list were scanned on 2026-09-13 and name none carrying it.
  • LMS / HSS, Primitive: Shipped BEFORE the lattice algorithms, which is the pattern across this category: stateful hash-based signatures were standardised first (SP 800-208) and the hardware followed first. Thales states the trade-off plainly on the same page – LMS-HSS keys are “not being copyable, thus no backup and no HA replication are possible”, which is state management showing through into operations.
  • LMS / HSS, FIPS 140-3: Inside Luna T7, Thales Trusted Cyber Technologies, FIPS 140-3 certificate 5450 issued 2026-07-29. Sunset 2031-07-28.
  • LMS / HSS, Firmware signing: The security policy for certificate 5450 states it outright: “The Firmware component is digitally signed using a Thales TCT Manufacturing signature key using RSA (4096 bits) PKCS #1 V1.5 with SHA2-384.” So the device that holds validated ML-KEM, ML-DSA and LMS for its customers verifies its own firmware with RSA. THE PATTERN ACROSS THIS CATEGORY, now evidenced rather than suspected: the hardware security modules that hold FIPS-validated post-quantum algorithms FOR CUSTOMERS still sign their OWN firmware classically. Thales Luna T7 uses RSA-4096, Entrust nShield 5s uses RSA-4096, Utimaco uses ECDSA. Crypto4A is the exception and dual-signs with HSS. This is exactly what the firmware column was added to expose: a module whose customer keys are post-quantum and whose root of trust is RSA has moved the problem rather than solved it, and the firmware signing key is the longest-lived key in the device.
  • XMSS / XMSS^MT, Primitive: TWO SOURCES, NEITHER MENTIONING IT, one of them exhaustive. The 89-page security policy for certificate 5450 does not contain the string XMSS ANYWHERE – while mentioning LMS 139 times and ML-DSA 68 – and a security policy has to describe the module’s non-approved services as well as its approved ones, so silence there is close to conclusive for the module. Thales’s own post-quantum documentation agrees, naming LMS-HSS, ML-KEM and ML-DSA and no other family. Read narrowly: this is the module and the documented product, not a promise about future firmware. Crypto4A holds SLH-DSA on an issued certificate today, so this is a product difference rather than a hardware limitation.
  • XMSS / XMSS^MT, FIPS 140-3: Not in any module of this project: the CMVP validated list and the Modules In Process list were scanned on 2026-09-13 and name none carrying it.
